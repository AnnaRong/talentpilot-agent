# iTalent 全流程审计口径

## 采集范围

默认是当前授权租户下用户可见的招聘流程和岗位；用户指定岗位、部门、日期或岗位状态时，只纳入明确命中的范围。每次运行先记录：

- 采集时间（使用当前机器的实际时间和时区）；
- iTalent 租户、产品和当前用户；
- 目标岗位范围与是否包含关闭岗位；
- 浏览器任务空间和页码检查点；
- 已采集、未采集、未展示和无法核验的字段。

## 岗位主数据

至少尝试读取：

`department`, `team`, `job_name`, `job_id`, `job_status`, `hiring_manager`, `request_owner`, `publisher`, `recruiter`, `screening_owner`, `hc`.

只记录页面明确的角色。招聘负责人、需求发起人、职位创建人、用人经理、筛选人和面试安排人不能互相替代。字段没有在页面显示时填 `未展示`，不要通过姓名、部门或历史记录推断。

## 候选人键与阶段

候选人的应聘关系使用：

```text
candidate_id + job_id
```

如果当前接口提供更完整的关系键，优先使用：

```text
applicant_id + apply_id + job_id
```

为每条关系保存当前阶段、当前状态、最近转移时间、来源页面和稳定详情链接。当前阶段只能说明采集时存量，不能反推出历史通过或淘汰事件。

## 初筛、复筛和面试

- 初筛简历数来自岗位级初筛列表或明确历史事件；不能用岗位总应聘者数代替。
- “通过初筛”必须有明确的通过状态或历史转移证据。
- 一面、二面、三面按实际面试记录分别保存：候选人、预约时间、状态、安排人、实际面试官、结果、评价人、评价时间和面评正文/摘要。
- 未来预约是“已安排/未完成”，不能算通过或淘汰。
- `未评价`、`已取消`、候选人拒绝、未到场、面试官淘汰要保持不同状态。
- 多人面试如只显示人数，写 `多人会议，姓名未展示`。

## 面评

每条面评必须能回溯到：

```text
job_id, candidate_id/apply_id, round, interviewer, interview_time, result, evaluated_at, source
```

报告中分开列出：

1. 明确淘汰的面评；
2. 明确通过的面评；
3. 未评价、无正文、只有分数或只有阶段结果的记录；
4. 面试官之间不一致的记录。

面评只做忠实摘录或短摘要，区分“评价者意见”和“系统流程结论”，不做人格、健康、婚育、年龄等敏感推断。

## 通过率与 Offer

只用完成的明确结果计算：

```text
本轮通过率 = 明确通过 / (明确通过 + 明确淘汰)
```

未评价、未来预约、取消、未到场、候选人拒绝和当前阶段人数不进入分母。`拟录用`不等于 Offer；只有页面明确显示已发放/已发送才计入 Offer。Offer、接受、拒绝、撤回、过期、待入职和已入职分别保留。

## 浏览器与恢复

- 先通过 `ego-browser` 打开 `https://www.italent.cn` 的主入口，让前端重新生成当前上下文；不要直接复用过期的 `cloud.italent.cn` 动态签名 URL。
- 登录需要扫码、短信、验证码或租户选择时，把可见页面交给用户；用户确认继续后再接管。
- iTalent 常见外层壳和业务 iframe 并存；外层文本不等于业务列表，必要时使用 `Page.getFrameTree` 找到当前业务 frame。
- 每完成一个岗位、阶段或页面立即写入 checkpoint；分页未完成时不得报告“已完整统计”。
- 若“职位”点击后仍停留首页或出现通用错误，报告导航阻塞并请用户手动打开模块，不报告空数据。
